1. Por que precisamos de um processo ETL

Cada fonte de dado tem sua própria estrutura, formato e qualidade — juntar tudo "no olho" não escala e não é confiável.

OrigemProblema encontrado
Loja físicaDatas no formato 15/01/2024; valor como texto "R$ 45,90"
E-commerceDatas no formato 2024-01-15; cliente às vezes sem país informado
AmbasAlguns pedidos aparecem duplicados; colunas em ordens diferentes

ETL (Extract, Transform, Load) é o processo que extrai, transforma e carrega dado de forma controlada — não é só "copiar dado pra um banco", é prepará-lo pra ser confiável.

2. Extração com Python

O primeiro passo é trazer os dados de cada origem pro Python, numa estrutura que dá pra inspecionar: fonte de dados → Python → análise inicial.

-- lendo e inspecionando as duas origens
import pandas as pd

loja_fisica = pd.read_csv("vendas_loja_fisica.csv")
ecommerce = pd.read_csv("vendas_ecommerce.csv")

print(loja_fisica.shape, ecommerce.shape)
print(loja_fisica.dtypes)
print(loja_fisica.isna().sum())
VerificaçãoO que revela
.shapeQuantas linhas e colunas cada origem trouxe
.dtypesSe cada coluna está no tipo esperado
.isna().sum()Quantos valores estão ausentes, coluna a coluna

3. Qualidade dos dados

Nem todo problema de qualidade é do mesmo tipo — e cada um pede uma decisão diferente:

Tipo de problemaExemplo
Valores ausentesPaís não informado em alguns pedidos
Tipos incorretosValor guardado como texto ("R$ 45,90")
Formatos diferentesData em dois formatos diferentes na mesma base
DuplicidadesO mesmo pedido aparecendo mais de uma vez
⚠️ Antes de corrigir, é preciso compreender: qual é o significado real daquele dado, qual a regra de negócio por trás dele, e qual o impacto da transformação sobre quem vai analisar isso depois. Corrigir sem entender o contexto pode criar um problema pior que o original.

4. Transformação

Toda transformação segue a mesma sequência: dado original → identificação do problema → regra de tratamento → dado transformado.

AntesDepois
data = "15/01/2024" (texto)data = 2024-01-15 (tipo data)
valor = "R$ 45,90" (texto)valor = 45.90 (tipo numérico)
país ausentepaís = "Brazil" (regra: origem loja física = Brasil)
pedido duplicadopedido único, mantendo o registro mais completo
-- aplicando as transformações
vendas["data"] = pd.to_datetime(vendas["data"], dayfirst=True)

vendas["valor"] = (vendas["valor"]
    .str.replace("R$", "", regex=False)
    .str.replace(",", ".", regex=False)
    .astype(float))

vendas = vendas.drop_duplicates(subset="id_pedido")

Depois de tratados, os dados ainda precisam ser mapeados pra estrutura que o PostgreSQL espera: DataFrame → mapeamento → tabela PostgreSQL.

6. Carga no PostgreSQL

Com os dados tratados e mapeados, a carga segue o mesmo fluxo que você já domina desde a Semana 11: Python → conexão → PostgreSQL → tabela de destino.

-- carregando os dados tratados
import psycopg2

conexao = psycopg2.connect(host="localhost", dbname="distribuidora",
                            user="postgres", password="...")
cursor = conexao.cursor()

dados = list(vendas.itertuples(index=False, name=None))
cursor.executemany(
    "INSERT INTO orders (order_id, order_date, total_amount, sales_channel) "
    "VALUES (%s, %s, %s, %s);", dados)
conexao.commit()

7. Validação

❓ O código terminou sem erro. Podemos considerar o ETL concluído? Executar sem erro e produzir um resultado correto são coisas diferentes. Um processo pode "funcionar" e mesmo assim entregar dado errado — sucesso da execução ≠ qualidade do resultado.

Validar significa confirmar: a quantidade de registros na origem bate com a carregada? Existem registros rejeitados? Os tipos e valores fazem sentido? Ainda restam duplicidades?

-- comparando origem e destino
total_origem = len(vendas)
cursor.execute("SELECT COUNT(*) FROM orders;")
total_destino = cursor.fetchone()[0]
print(f"Origem: {total_origem} | Destino: {total_destino}")
# se os números não baterem, algo foi perdido ou duplicado

8. Falhas, reprocessamento e rastreabilidade

Uma carga pode ser interrompida no meio do caminho — parte do dado já está no banco, parte não. Rodar o processo de novo sem cuidado pode duplicar o que já foi carregado com sucesso.

ConceitoPor que importa
Transação (Semana 10)Agrupa comandos: ou tudo é confirmado, ou nada é
Identificador únicoPermite reconhecer o que já foi carregado antes de inserir de novo
IdempotênciaRodar o mesmo processo várias vezes leva sempre ao mesmo resultado
Rastreabilidade (log)Registra quando rodou, quantos registros, e o que deu certo/errado

9. O pipeline ETL consolidado

Juntando tudo que esta aula trabalhou, um pipeline ETL confiável segue este fluxo:

FONTE → EXTRAÇÃO → VALIDAÇÃO INICIAL → TRANSFORMAÇÃO → PREPARAÇÃO → CARGA → VALIDAÇÃO FINAL → REGISTRO DA EXECUÇÃO
