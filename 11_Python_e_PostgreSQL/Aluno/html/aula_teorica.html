1. Python + PostgreSQL: a conexão de ponta a ponta

Desde a Semana 08 você já testa a conexão com psycopg2. Esta semana você domina o fluxo completo: Python → conexão → PostgreSQL → tabela → resultado → Python.

PeçaPapel
psycopg2.connect(...)Abre a conexão (host, dbname, user, password)
conexao.cursor()Cria o cursor — o objeto que executa comandos SQL
cursor.execute(sql)Envia o comando SQL pro banco
cursor.fetchall() / fetchone()Recupera o resultado de volta pro Python
conexao.close()Encerra a conexão — sempre, ao final
⚠️ Sempre trate o erro de conexão. Um try/except psycopg2.OperationalError evita que a aplicação quebre feio se o PostgreSQL estiver desligado ou a senha estiver errada — o mesmo padrão que você já usa desde a Semana 08. 
-- fluxo completo: conectar, consultar, encerrar
import psycopg2
conexao = psycopg2.connect(host="localhost", dbname="distribuidora", user="postgres", password="...")
cursor = conexao.cursor()
cursor.execute("SELECT company_name, country FROM customers LIMIT 5;")
resultado = cursor.fetchall()
conexao.close()

2. Executando SQL pelo Python

O Python não substitui o SQL — ele CONTROLA quando e como o SQL roda. O fluxo é sempre: necessidade → SQL → Python → PostgreSQL → resultado → Python.

-- consulta com filtro, controlada por código
cursor.execute("SELECT company_name, city FROM customers WHERE country = %s;", ("Brazil",))
clientes_brasil = cursor.fetchall()
💡 Por que %s em vez de colar o valor direto no texto? Usar um parâmetro (%s + uma tupla de valores) protege contra erro de sintaxe com aspas e, principalmente, contra SQL Injection — nunca monte SQL concatenando texto do usuário direto na string.

3. Manipulação de Dados: INSERT e UPDATE programáticos

As mesmas regras de SQL que você já conhece (Semana 10) valem aqui — só que agora quem decide QUANDO rodar é o código Python, não você digitando manualmente.

-- inserindo um novo produto, com parâmetros seguros
cursor.execute(
    "INSERT INTO products (product_name, category_id, unit_price) VALUES (%s, %s, %s);",
    ("Café Especial 500g", 1, 28.90),
)
conexao.commit()

-- atualizando um preço, com WHERE sempre presente
cursor.execute("UPDATE products SET unit_price = %s WHERE product_name = %s;", (32.50, "Café Especial 500g"))
conexao.commit()
⚠️ conexao.commit() é obrigatório depois de INSERT/UPDATE/DELETE — sem ele, a alteração fica só na sessão aberta e não é salva de verdade no banco.

4. Surge um novo problema: o projeto cresceu

O banco da Vetor Distribuidora já tem várias tabelas relacionadas — customers, products, categories, suppliers, orders. Cada nova operação (SELECT, INSERT, UPDATE, JOIN) vira mais um trecho de SQL espalhado pelo código Python, cada um com sua própria string de comando. Isso levanta uma pergunta: existe uma forma de aproximar o mundo dos objetos Python do mundo relacional do banco?

A resposta é o ORM — Object-Relational Mapping: uma camada que representa cada tabela como uma classe Python, e cada linha como um objeto — sem eliminar o SQL por baixo, só evitando que você precise escrevê-lo à mão toda vez.

5. SQLAlchemy: tabela vira classe

SQLAlchemy é o ORM mais usado em Python. Ele mapeia:

Banco de DadosPython
TabelaClasse
ColunaAtributo
Registro (linha)Objeto
-- mapeando a tabela products como uma classe
from sqlalchemy import create_engine, Column, Integer, String, Numeric
from sqlalchemy.orm import declarative_base, Session

Base = declarative_base()

class Product(Base):
    __tablename__ = "products"
    product_id = Column(Integer, primary_key=True)
    product_name = Column(String)
    unit_price = Column(Numeric)

engine = create_engine("postgresql://postgres:senha@localhost/distribuidora")
with Session(engine) as sessao:
    produtos = sessao.query(Product).all()
    for p in produtos:
        print(p.product_name, p.unit_price)  # acessando coluna como atributo do objeto

Repare: em nenhum momento você escreveu SELECT * FROM products — o SQLAlchemy monta esse SQL por trás, a partir da classe Product.

6. SQL Direto x ORM

SQL Direto (psycopg2)ORM (SQLAlchemy)
Controle sobre a consultaTotal — você escreve exatamente o SQLMenor — o ORM decide o SQL gerado
ProdutividadeMais código repetitivoMais rápido pra operações comuns
Organização do códigoSQL espalhado pela aplicaçãoDado representado como objeto
Flexibilidade para consultas complexasAltaPode exigir SQL "cru" mesmo assim
⚠️ ORM NÃO elimina a necessidade de conhecer SQL. Toda consulta gerada pelo ORM ainda é SQL por baixo — entender o que está sendo executado continua sendo essencial pra depurar e otimizar.

A escolha entre SQL direto e ORM depende do contexto: complexidade da consulta, necessidade de controle fino, produtividade da equipe, e características do próprio projeto — não existe uma resposta "sempre certa".
